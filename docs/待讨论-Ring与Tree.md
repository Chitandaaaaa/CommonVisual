# 待讨论 · Ring 与 Tree 的区别

> 这份文档不是教程，是**待办清单 + 背景资料**。
> 起因：reduce 页面目前画的是「三份整份依次飞进 root」，这其实不是 NCCL 的默认做法。
> 需要先想清楚「页面要不要为真实性让步」，再决定要不要加新视图。

---

## 一、先对齐一件事：页面现在画的是什么

页面画的是 **Star / Direct Reduce**：

```
rank1 ──┐
rank2 ──┼──▶ rank0（边收边加）
rank3 ──┘
```

- 每一份都是**整份 4 段**飞过去，root 收到一份就立刻逐段折进累加器
- 优点：和 gather / broadcast 共用「整份数据」这套视觉语言，语义最容易看懂
- 缺点：**它不是 NCCL 的实现方式**。真实世界里没人这么干 —— root 的入口带宽会被打爆

所以这一页现在的定位是「**语义示意**」，不是「实现示意」。要不要在页面上把这句话点出来，是第一个待讨论项。

---

## 二、Ring 和 Tree 到底差在哪

两者都在解决同一个问题：**别让 root 一个人接所有数据**。

### Ring：把数据切碎，绕圈传递

N 张卡围成一个环，把一份数据切成 N 块，然后做 **reduce-scatter**：每一步每张卡把手里的一块发给下游、同时从上游收一块并累加。走 N−1 步之后，每张卡手里都有一块「已经归约好」的块。

- **步数**：2(N−1)（all-reduce 要再做一遍 all-gather 把结果铺开；纯 reduce 只需前半程 + 各块汇总到 root）
- **每卡搬运量**：≈ 2(N−1)/N · M，N 大时接近 2M —— 这就是「带宽最优」的含义
- **延迟**：∝ N。N 越大，绕的圈数越多
- **强项**：大消息。每条链路始终在满负荷工作

### Tree：分层归约，log 步搞定

把 N 张卡组织成二叉树，叶子往父节点传，父节点先加再往上，root 只收两个子树的结果。

- **步数**：2·log₂N（上行归约 + 下行广播）
- **每卡搬运量**：每一层都搬**整份** M，所以带宽项 ≈ 2·log₂N·M —— 比 Ring 差
- **延迟**：∝ log₂N。N = 256 时 Ring 要 510 步，Tree 只要 16 步
- **强项**：小消息 / 超大规模。延迟主导的时候，Tree 完胜

### 一张表

| | Ring | Tree |
|---|---|---|
| 数据切分 | 切成 N 块 | **不切**，整份走 |
| 步数 | 2(N−1) | 2·log₂N |
| 延迟 | ∝ N（线性，规模大就崩） | ∝ log₂N |
| 每卡搬运量 | ≈ 2·(N−1)/N·M（接近 2M） | ≈ 2·log₂N·M（更大） |
| 带宽效率 | **最优**，链路不空闲 | 次优，中间节点要转发整份 |
| 适用 | 大消息、单机 NVLink 域、张量并行 | 小消息、跨机跨柜、上千卡 |
| NCCL 里支持 | 五个原语全覆盖 | 主要给 all-reduce（双二叉树） |

### NCCL 怎么选

不是静态阈值，是运行时按「消息大小 + 拓扑 + 卡数」构建一个经验模型，每次调用现场判断：

| 场景 | 倾向 |
|---|---|
| 小消息（KB 级、barrier、标量） | Tree —— 延迟主导 |
| 大消息（梯度、权重） | Ring —— 带宽主导 |
| 8 卡单机 NVLink 全互联 | Ring 一直占优（链路过短，Tree 没啥优势） |
| 上百卡、跨机 | Tree 或 NVLS —— Ring 的延迟和带宽同时退化 |
| 有 NVSwitch / SHARP | NVLS / CollNet —— 归约直接在交换机里做，谁都不用在卡上算 |

> 单机 8 卡 H100 上，交叉点大约在 **256 KiB** 左右：比它小，Tree 更快；比它大，Ring 更快。
> 这个数字随硬件变，不要当常数记。

**小结**：Ring 赌带宽，Tree 赌延迟。规模越大，Tree 越划算；机器越「小」，Ring 越划算。

## 三、待讨论的问题

### Q1. 要不要在页面上标注「这是 Star，不是 NCCL 默认」
- 加一句脚注的成本很低，但会打破现在「一屏只有舞台和字幕」的极简
- 不加的话，读者容易把这张图当成真实实现

### Q2. 要不要做 Ring 视图
难点在**视觉**，不在代码：

- 现在全站的数据单位是「整份 4 段」，所有卡都是 4 个槽
- Ring 要求把整份切成 N 块，每张卡每步只拿一块 → 槽位语义要重做
- 环形布局（卡片围成一圈）与现在的「左 dst / 右 src 竖排」完全不同，等于另开一套版面

如果做，可能的折中：
- **不画环**，仍然左右排，只用连线的**方向与编号**表达「绕圈」（第 1 步 rank1→rank2，第 2 步 rank2→rank3…），配一条环形箭头示意
- 或者做成「环 + 舞台中央的当前块」：中央显示这块数据现在在谁手里、累加了几次

### Q3. 要不要做 Tree 视图
比 Ring 容易：树形本来就适合竖排/分层画。

- 但 Tree 在 NCCL 里主要服务 all-reduce，和本页的 reduce 主题不完全对得上
- 要做的话，可能更适合放在 **all-reduce** 那一页，而不是 reduce

### Q4. 五个原语页面要不要统一加一个「算法」切换
- 现在五页（gather / scatter / broadcast / reduce + 完整版）都是「一种画法讲清语义」
- 加切换会引入第二套时间轴、第二套几何，维护成本翻倍
- 反方观点：算法对比本身可能比单个原语的动效更有教学价值

### Q5. 如果要讲「为什么不是 Star」，说明放在哪
候选：
1. 页面字幕的某一步（挤，且破坏节奏）
2. 页面底部一行小字（最轻）
3. 单独一页「实现 vs 语义」（最重，但最干净）
4. 就放在本文件里，页面不动

## 四、结论待定

目前倾向：**reduce 页面保持 Star 画法不动**，因为它的价值是「让人第一次看懂 reduce 在干什么」；
Ring / Tree 属于「知道了之后才想知道」的第二层，硬塞进同一屏会把两个层次搅在一起。
