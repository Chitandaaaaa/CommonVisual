Blueprint · v2

组件库与代码架构

只问一件事：要讲清这套东西，需要哪些零件？
从这个问题出发，得到 32 件组件、5 类页面、6 层架构，以及 5 个写明形状的扩展点。

32组件 5类页面 4动作原语 8份剧本 6层依赖 5个扩展点 0组件互相引用
v2 相对 v1 改了三处，都是 v1 的错。 ① v1 只看了 8 个原语页，漏了首页关系树、前后对照表、算法骨架页、规范页 —— 这四页占需求的一半，却一件组件都没配。 ② 因此 v1 的「需求 → 模型」推导只推出了舞台概念，把另外五条需求硬塞进了同一套动画模型。 ③ v1 没有回答「加一个原语 / 加一个动画 / 加一个数据块要改哪里」，等于没写扩展性。 本页 01、02、04 已按这三件事重写，另加 05 页面族、07 扩展点。
01

先把需求变成模型

这个项目要讲的东西，本质上只有一句话：一份数据从哪来、经过什么、到哪去。 8 个原语不是 8 份代码，是这句话的 8 种特例。 所以先定模型，再定零件 —— 零件的分类依据不该是「长得像」，而是它回答哪一个问题。 这一节先推「过程」那一支，另一半紧接着补。

需求不会直接变成代码。中间必须过一道「概念」 —— 概念定了，组件和架构才有依据。
但这张图只覆盖了一半需求。 左列五条里，只有第 1 条（8 个原语各要一段动画）是「过程」，其余四条都是「把同一批事实换个摆法」。 v1 把这四条也塞进了舞台五概念，于是首页、对照表、算法页、规范页在组件库里没有位置。 正确做法是先分叉，再各自成模型。
需求先分「过程 / 呈现」两支。过程出五概念，呈现出一份事实表 —— 组件库要同时服务这两支。
02

组件库 · 32 件

每件只做一件事，只认自己的输入，不知道「原语」这个词存在。 舞台不知道谁是 gather，演员不知道数据要去哪 —— 只有编排层知道。 32 件分七组：前三组画「过程」，N 组画「关系」，Bk 组搭「页面骨架」，X 组装「播放器」。

32 件按「服务于哪一步」分组，不按图形类型分。同组内部互不引用，组合权在引擎。

「存在的理由」这一列是硬约束。任何组件如果答不上「它回答哪个问题」，就不该存在。 反过来，任何一个问题如果没人回答，就说明组件库漏了东西 —— 这一列是组件库的自检清单。

03

八个原语，四个动作

组件库够不够用，取决于抽象的粒度对不对。验证办法：看 8 个原语能不能全部拆成同一批动作的组合。 能，则引擎只需实现 4 个动作；不能，则抽象错了。

这张表就是「抽象是否够用」的证明。填不满 4 列，说明动作少了；溢到第 5 列，说明抽象错了。
四个动作的判据（不写清就会各人各判）： move＝一段数据从源槽飞到目标槽 —— 源槽留不留是剧本里的槽位状态，不是动词的属性 （gather 源卡保留、scatter 起飞即清空，用的都是 move）； copy＝整份数据原样复制到另一张卡（只有 broadcast 用）； split＝把一组段从整份里拆出去飞（源槽在起飞那一刻清空）； sum＝飞到累加器并逐段折算（计算框是它的伴生块）。 「复制还是消耗」永远读剧本的 cast 终态（对照表 pre/post），不读动词名。
由此得到一条可执行结论：新增原语 = 一份剧本 + 一行事实，不改引擎。 剧本是纯数据（演员表 + 节拍序列 + 终局），不含任何绘制代码；事实表那一行负责「它叫什么、连到谁、前后各持有什么」。 两者都不是代码逻辑 —— 所以新增原语第一次变成一件可以完全并行、不与别人冲突的任务。
但这张表本身有个前提：它是手填的，所以它会过期。 今天填满 4 列，是因为有人肉眼核对过 8 行。第九个原语进来，没人会记得回来改这张表 —— 现有代码里同一类事实手抄了 4 处（首页树 / 关系导航 / 对照表 / 算法矩阵），已经吃过这个亏。 所以这张表要变成 registry.js 的渲染结果，而不是文档里的一张图： 一条原语记录声明自己用到哪几个动词，tools/verbs.mjs 扫一遍就能报「出现了第 5 个动词」或「某行是空的」。 详见 07 的 E2 / E3。
04

代码架构 · 六层

分层的唯一判据：改上一层，不需要动下一层。 每层只认识它下面那层，不跨层调用，不认识「原语」这个概念 —— 除了最上面的页面。

层级越靠上，可并行的切口越多。真正排队的只有 L0 令牌和引擎主循环 —— 层内都按文件切开了。

① 组件不自组合
parts/* 之间零引用。谁和谁拼在一起，由引擎决定。这样任何一件都能单独替换、单独测试。
② 剧本是纯数据
scenes/* 里不许出现绘制调用、DOM 操作、定时器。必须能 JSON.stringify 通过。这样剧本可以被校验、被 diff、被参数化。
③ 只有引擎碰时间
组件不知道「现在几点」，只接受一个 t 并渲染出这一帧。全局只有一个 requestAnimationFrame。
④ 原语事实只有一份
名称、方向、前后状态、邻居、算法行，全在 registry.js。页面不许在自己文件里再抄一遍 —— 现有代码同一桩事实抄了 4 处，改一处漏三处。
⑤ 组件按组切开
parts/ nav/ blocks/ 三组之间不互相引用，同一组内的文件之间也不引用。三条泳道可以三个人同时改。
为什么保留「全局命名空间 + 十来个 script 标签」而不是 ES Module？ 因为「双击 html 就能看」是这个项目的硬需求 —— 要能直接发给同事、丢进文件夹就打开。 ESM 在 file:// 下会被 CORS 拦，必须要起本地服务。 所以模块化让位，改用 defer 保证顺序，每个文件只往 CV 上挂一个子命名空间。
05

五类页面 · 一份事实的五种投影

现有 12 个 html 不是 12 个功能，是 5 类页面。分类判据只有两条： 要不要时间轴、画的是不是「数据在动」。这两条决定了用哪几组组件。

五类页面共 12 个 html，只有 8 个是动画。组件库必须同时覆盖「动」和「不动」。

舞台需要时间轴

八个原语页。全站唯一需要「第几帧」的地方：唯一 rAF、分段进度、可拖动。

约束：单屏不滚动、viewBox 等比缩放、卡片可长高不换页。

关系树入场动效，不是动画

首页。动效只发生在「第一次进视口」：节点错峰上浮、连线描边生长。之后完全静止，没有播放器。

约束：树是 8 节点 8 连线的固定图。现页面把手排在 HTML 的 grid 行列上； 新实现改为从 registry 的 rel[] 用固定算法推出同样的行列（列 = 链，行 = 父节点所在行顺延），不跑自动布局。

对照表状态，不是过程

只回答「通信前每卡有什么、通信后变成什么」。中间一个动作词，两边各四行格子。

约束：未变化的行整行置灰；结果卡加紫描边；空格是虚线框。

文档 / 规格排版与自测

算法骨架页只有矩阵表和卡片；规格页把每个组件单独挂出来，配尺寸线和 tab。

约束：规格页必须调真实组件渲染，不能画示意图 —— 否则规范会漂移。

最难的一处取舍：对照表的格子要不要复用 cast.slot？ 现在的实现是不复用 —— 舞台用 SVG <rect>，对照表用 HTML <i>，尺寸也不同（46 对 20）。 我建议保持不复用，理由只有一条：对照表的行要能被 CSS 整行置灰、要能随宽度换行、要能放 6 个以上格子， SVG 这三件事都做不到。强行统一会让舞台多背一套流式布局，或让对照表失去置灰能力。 正确的复用层次是语义与令牌：同一份四色、同一套 A/B/C/D/Σ 字母、同一份 registry 前后状态数据； 渲染各写一份薄的。代价写在这里，免得以后有人以为是漏了。
06

运行时 · 一条时间轴

整个架构里最关键的取舍在这里。组件做不到「有状态」，是刻意的 —— 一旦每个动效自己保管定时器，暂停、倍速、跳步、切视图就都要各写一份清理逻辑，漏一处就卡住。

五件操作背后只有一件事：改变 t 的推进方式。这是「组件无状态」换来的全部好处。

剧本长什么样

export default {
  id: 'gather',
  cast: [
    { id: 'r0', label: 'rank 0', slots: 4, at: 'left'  },
    { id: 'r1', label: 'rank 1', slots: 1, at: 'right.0' }
  ],
  beats: [
    { kind: 'wait', label: '三张卡各持一份', sec: 0.9 },
    { kind: 'move', from: 'r1/0', to: 'r0/3', tone: 'B', path: 'arc', sec: 1.2 },
    { kind: 'seat', target: 'r0/3', sec: 0.35 }
  ],
  finale: 'rank 0 集齐 A B C D，其余三张卡各留自己那段（复制，不是消耗）'
}

四个 kind —— move / copy / split / sum，加上 wait 与 seat 两个表现节拍， 就构成了 8 个原语的全部剧本。新增原语不需要新的 kind。

07

扩展点 · 加东西时要改几个文件

开闭原则落到这个项目上只有一句话：加东西时，新文件越多越好，改老文件越少越好； 如果非改不可，改的必须是数据，不是逻辑。 下面五个扩展点是这件事可执行的部分 —— 每个都写明「形状」，因为没写形状的扩展点等于没有。

扩展点必须写清形状和消费者，否则只是口号。

走查 · 三个真实需求撞上去
A · 加一个动画
需求：「数据包飞过去的时候，目标格先闪一下再接住」。

判断：这不是新动词，是新节拍。现有 beat.dim 管「只留相关几份」，管不了「提前预告」。

做法：parts/beat.js 里加 beat.anticipate(target, sec)，剧本在 seat 前插一条。
代价：新文件 0，但要动 B 组 —— B 组是串行区。若走 E3 硬做成动词，就会污染「动作」语义（它是表现层，不是搬运层）。
B · 加一个原语
需求：加第 9 个原语。

做法：registry 加 1 条（含 rel[] 边列表——All-Reduce 有两条入边，单亲的 after 字段写不下，所以关系必须是边的集合而不是父指针）+ 1 份剧本 + 1 个 html。

树的位置不手排 —— nav 读 rel 算列。这是第一次要写约 40 行列分配算法的代价，之后新增永久免费。

撞不过的地方：algorithms 的算法矩阵按「6 种骨架 × 8 原语」手填，第 9 行仍要人判断能不能走通 —— 这一格只能人填，不能自动生成。
C · 加一个数据块
需求：从 4 块变成 6 块。

可用宽 = 300 − 20×2 = 260；n 块 = n×46 + (n−1)×12：
n=4 → 220 ✓　n=5 → 278 ✗　n=6 → 336 ✗

所以第 5 块就溢出了。三条出路：折第二排（卡片长高，已有先例）/ 缩槽到 36（字挤）/ 溢出滚动（最差）。

做法：E4 把「装不下怎么办」写成参数，剧本只写 slots: 6。但折行会改卡片高度，线上所有下落点都要重算 —— 这一步必须引擎算，不能靠改数据。
做不到开闭的三件事，写在这里免得以后吵架： ① 改交互模型（点卡片钻取、拖动重排）→ 必须动引擎，因为「谁在哪一帧被点到」是新概念； ② 改时间语义（从按秒改成弹簧/物理）→ 必须动动词，每个 plan() 的返回值要换； ③ 换渲染后端（SVG → Canvas）→ L2 整层重写，组件契约里的 element 会换成绘制指令。 这三件不是设计没做好，是需求类别变了。把它们当成「扩展」来承诺，才是骗人。
08

并行边界

架构的价值最终体现在：两个人同时改，会不会撞。按上面的分层，答案分三档 —— 页面 / 剧本 / 动词随便并行，组件按组并行，令牌与引擎主循环排队。

层文件谁能改并行性改完要验
L5 *.html ×12 一个人一页 完全并行 该页截图
L4 scenes/*.js ×8 一个人一份 完全并行 该页动效 + 终局
L4 registry.js 一条原语一行，一人一行 基本并行 树 / 对照表 / 文档全走一遍
L3 engine/verbs/*.js 一个人一个动词 完全并行 动词矩阵重扫
L3 engine/{clock,director,compile} 排队，一次一人 串行 八页动效全跑一遍
L2 parts/ · nav/ · blocks/ 一组一人，组内排队 三组并行 规范页 + 用到该组的页
L1 prim/*.js 排队 串行 全站
L0 theme/* 排队 串行 全站
一句话判断：只动 scenes/、verbs/ 或 *.html → 随时开工，不会撞人。 动 parts/ nav/ blocks/ → 先问一句「现在有别人在改同一组吗」。 动 prim/ theme/ 或引擎主循环 → 全站排队。 这条界线之所以清楚，是因为下面四层里没有任何一个文件认识「原语」　—— 它们改动的动机永远来自抽象层，不来自某一页。
唯一一个跨人共享的写点是 registry.js。 它必须是单文件（否则又变成多处手抄），而 8 条记录挤在一个文件里，两个人同时加原语必然冲突。 缓解办法就一条：一条原语严格占固定行数的连续区间，且文件按 id 字母序排列。 这样 git 的冲突粒度落在一段，不会牵动别人的段落 —— 但不能消除冲突，只能把它压到「解一次小冲突」的量级。 这是这套架构里唯一没有干净解法的地方，写在这里而不是假装它不存在。

八个页面各自长什么样
八个页面不是八种动画，是同一批构件的八种组合 —— 表格里每一列对应引擎的一个能力

这些列落在哪些组件上：双排槽 = cast.row + geom.plan；Σ 角标与头部徽章 = cast.badge； 轮次字幕 = chrome.cap；对角连线 = payload.edge 的直线中心交叉（早期 bend 方案已删除，见 AGENTS 三）；终局一句话 = 剧本的 finale 字段。 只有「计算框」没有独立组件 —— 它是 beat.fuse 合并动作的伴生块，离开合并就没有意义，单独成件反而是多余的抽象。

哪些必须一致、哪些可以不一样、哪些现在就不统一
必须一致 · 0 差异
卡片与槽的尺寸圆角 · 四条数据色 · 虚线弧与端口圆 · 数据包带递减尾巴 · 落位弹跳（不回弹、无涟漪）· 卡片长高而非换页 · 字幕内联彩色标签 · 右上齿轮 + 底部三段按钮
允许不同 · 不参与比对
文件名与目录 · DOM 层级与类名 · 加载方式 · 每帧重绘还是局部更新 · 组件拆到多细 · 参数存在哪
现在不统一 · 新实现定一个
顶部图例有的左对齐有的居中 · 关系写法混用「↓ Scatter」与「Reduce → All-Reduce」· 进度条段数不完全等于步骤数 · alltoall 终态四卡未齐平 · 字幕放四个 rank 标签时过挤 · 同一个「原语关系」在首页画成节点连线、在原语页左上角画成小卡，两套代码 · 页头有三套：index 的 hero、layout/algorithms/anatomy 的 .hd、原语页的 h1
怎么判定「一致」：固定视口 1180 × 800、deviceScaleFactor 1，在进度 0.30 / 0.60 / 0.99 三个时刻各截一张， 新实现与现页面叠合比。差异只允许出现在第二列清单里 —— 出现在第一列任意一条，就是不通过。 第三列不是缺陷清单，是当前没有唯一答案的地方，新实现必须先选定一个，再写进断言。
