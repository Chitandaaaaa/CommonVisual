组件库与代码架构

本页是 CommonVisual 组件库与代码架构的标准。只回答一个问题：要讲清 8 种原语，需要哪些零件？
从这个问题出发，得到 32 件组件、6 层架构，以及 5 个写明形状的扩展点。

32组件 4动作原语 8份剧本 6层依赖 5个扩展点 0组件互相引用
01

先把需求变成模型

这个项目要讲的东西，本质上只有一句话：一份数据从哪来、经过什么、到哪去。 8 个原语不是 8 份代码，是这句话的 8 种特例。 所以先定模型，再定零件 —— 零件的分类依据不该是「长得像」，而是它回答哪一个问题。

需求不会直接变成代码。中间必须过一道「概念」 —— 概念定了，组件和架构才有依据。
需求先分「过程 / 呈现」两支。过程出五概念，呈现出一份事实表 —— 组件库要同时服务这两支。
02

组件库 · 32 件

每件只做一件事，只认自己的输入，不知道「原语」这个词存在。 舞台不知道谁是 gather，演员不知道数据要去哪 —— 只有编排层知道。 32 件分七组：前三组画「过程」，N 组画「关系」，Bk 组搭「页面骨架」，X 组装「播放器」。

32 件按「服务于哪一步」分组，不按图形类型分。同组内部互不引用，组合权在引擎。

03

八个原语，四个动作

组件库够不够用，取决于抽象的粒度对不对。验证办法：看 8 个原语能不能全部拆成同一批动作的组合。 能，则引擎只需实现 4 个动作；不能，则抽象错了。

这张表就是「抽象是否够用」的证明。填不满 4 列，说明动作少了；溢到第 5 列，说明抽象错了。
四个动作的判据（不写清就会各人各判）： move＝一段数据从源槽飞到目标槽 —— 源槽留不留是剧本里的槽位状态，不是动词的属性 （gather 源卡保留、scatter 起飞即清空，用的都是 move）； copy＝整份数据原样复制到另一张卡（只有 broadcast 用）； split＝把一组段从整份里拆出去飞（源槽在起飞那一刻清空）； sum＝飞到累加器并逐段折算（计算框是它的伴生块）。 「复制还是消耗」永远读剧本的 cast 终态（对照表 pre/post），不读动词名。
由此得到一条可执行结论：新增原语 = 一份剧本 + 一行事实，不改引擎。 剧本是纯数据（演员表 + 节拍序列 + 终局），不含任何绘制代码；事实表那一行负责「它叫什么、连到谁、前后各持有什么」。 两者都不是代码逻辑 —— 所以新增原语第一次变成一件可以完全并行、不与别人冲突的任务。
这张矩阵的机器口径在 registry.js。每条原语用 verbs: ['move','sum'] 声明自己用到哪几个动作， 这张表就是 8 条声明铺开的样子。手填的表会过期：改动词先改 registry，再回来对这张表 —— 对不上，就是哪一边改漏了。
04

代码架构 · 六层

分层的唯一判据：改上一层，不需要动下一层。 每层只认识它下面那层，不跨层调用，不认识「原语」这个概念 —— 除了最上面的页面。

层级越靠上，可并行的切口越多。真正排队的只有 L0 令牌和引擎主循环 —— 层内都按文件切开了。

① 组件不自组合
parts/* 之间零引用。谁和谁拼在一起，由引擎决定。这样任何一件都能单独替换、单独测试。
② 剧本是纯数据
scenes/* 里不许出现绘制调用、DOM 操作、定时器。必须能 JSON.stringify 通过。这样剧本可以被校验、被 diff、被参数化。
③ 只有引擎碰时间
组件不知道「现在几点」，只接受一个 t 并渲染出这一帧。全局只有一个 requestAnimationFrame。
④ 原语事实只有一份
名称、方向、前后状态、邻居、算法行，全在 registry.js；轮次口径（几轮、每轮哪些边）在 rounds.js。页面不许在自己文件里再抄一遍。
⑤ 组件按组切开
parts/ nav/ blocks/ 三组之间不互相引用，同一组内的文件之间也不引用。三条泳道可以三个人同时改。
为什么保留「全局命名空间 + 十来个 script 标签」而不是 ES Module？ 因为「双击 html 就能看」是这个项目的硬需求 —— 要能直接发给同事、丢进文件夹就打开。 ESM 在 file:// 下会被 CORS 拦，必须要起本地服务。 所以模块化让位，改用 defer 保证顺序，每个文件只往 CV 上挂一个子命名空间。
05

运行时 · 一条时间轴

整个架构最关键的取舍在这里：组件无状态，是刻意的。 一旦每个动效自己保管定时器，暂停、倍速、跳步、切视图就都要各写一份清理逻辑，漏一处就卡住。 所以全站只有一个 rAF、一条时间轴。

五件操作背后只有一件事：改变 t 的推进方式。这是「组件无状态」换来的全部好处。

剧本长什么样

CV.scene('gather', function () {
  return {
    id: 'gather',
    preset: 'col34',                       /* 布局代号，坐标由 geom.plan 统一算 */
    cards: [
      { rank: 0, col: 'left',  role: 'dst', target: true },
      { rank: 1, col: 'right', role: 'src' }  /* …共 4 张 */
    ],
    beats: [
      { kind: 'wait', label: '说明', sec: 0.6, text: '四张卡各持一份' },
      { kind: 'move', label: 'B 传递', flows: [{ from: [1, 0], to: [0, 1], letter: 'B' }] },
      { kind: 'wait', label: '收尾', sec: 2,   text: 'rank 0 集齐 A B C D' }
    ],
    finale: 'rank 0 集齐 A B C D，其余三张卡各留自己那段'
  };
});

节拍的 kind 一共 6 种：wait / seat 两个表现节拍，加 move / copy / split / sum 四个动作 —— 8 份剧本全部由它们组成。 剧本是纯数据：无绘制调用、无定时器，能过编译器校验，能 diff。新增原语不需要新 kind。

06

扩展点 · 加东西时要改几个文件

扩展性只看一件事：加东西时，新文件越多越好，改老文件越少越好； 如果非改不可，改的必须是数据，不是逻辑。 下面五个扩展点是这件事可执行的部分 —— 每个都写明「形状」，因为没写形状的扩展点等于没有。

扩展点必须写清形状和消费者，否则只是口号。
五种变更，各自要动几个文件
想加什么新文件改已有文件会不会撞车
一个原语scenes/x.js · x.htmlregistry.js 加 1 条不会
一个动作engine/verbs/x.js用到它的页各加 1 行 script不会
一个数据块—剧本里 slots 改数不会
一类页面x.html · blocks/x.js—不会
一次改色—theme.css 一处全站一起变
走查 · 三个真实需求撞上去
A · 加一个表现节拍
「目标格先闪一下再接住」不是新动词，是新节拍：在 parts/beat.js 加 beat.anticipate(target, sec)，剧本在 seat 前插一条。
表现归 B 组，搬运归动词 —— 做成动词会污染「动作」语义。
B · 加一个原语
registry 加 1 条（rel[] 是边的集合，不是单亲指针 —— All-Reduce 有两条入边）＋ 1 份剧本 ＋ 1 个薄壳。
关系树由 rel[] 推列，不手排。只有算法矩阵那一格要人判断能不能走通。
C · 加一个数据块
卡内可用宽 260，n 块要 n×46 + (n−1)×12 —— n=5 起放不下（278 > 260）。
出路写进 E4 参数：折第二排 / 缩槽 / 滚动。折行会改卡片高度，全部下落点必须引擎重算，不是改数据能解决的。
07

并行边界

架构的价值最终体现在：两个人同时改，会不会撞。按上面的分层，答案分三档 —— 页面 / 剧本 / 动词随便并行，组件按组并行，令牌与引擎主循环排队。

层文件谁能改并行性改完要验
L5 *.html ×12 一个人一页 完全并行 该页截图
L4 scenes/*.js ×8 一个人一份 完全并行 该页动效 + 终局
L4 registry.js 一条原语一行，一人一行 基本并行 树 / 对照表 / 文档全走一遍
L3 engine/verbs/*.js 一个人一个动词 完全并行 动词矩阵重扫
L3 engine/{compile,director} 排队，一次一人 串行 八页动效全跑一遍
L2 parts/ · nav/ · blocks/ 一组一人，组内排队 三组并行 规范页 + 用到该组的页
L1 prim/*.js 排队 串行 全站
L0 theme/* 排队 串行 全站
一句话判断：只动 scenes/、verbs/ 或 *.html → 随时开工，不会撞人； 动 parts/ nav/ blocks/ → 三组可并行，组内先打招呼； 动 prim/、theme/ 或引擎主循环 → 全站排队，改完八页全跑一遍。 唯一共享写点是 registry.js：一条原语固定连续行区间、按 id 排序，把冲突压在段内不牵动别人。 这条界线之所以清楚，是因为下面四层里没有任何一个文件认识「原语」。
